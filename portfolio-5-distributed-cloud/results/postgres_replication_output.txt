C5  Stale read (eventual consistency) - replica deliberately applies WAL 3 s late
========================================================================================
primary: row inserted and committed
replica, immediately: rows with note 'stale-read test' = 0   <- stale
replica, after 3.1 s: rows = 1   <- consistent again
Lesson: a clinician who saves a prescription and is then routed to a lagging replica may not see it.
GraceCare therefore sends read-your-own-writes traffic (clinical screens) to the primary and only
reports/dashboards to replicas.

========================================================================================
C6  Synchronous vs asynchronous commit - latency cost of zero data loss
========================================================================================
     application_name | sync_state 
    ------------------+------------
     replica1         | sync
    (1 row)
200 single-row autocommit INSERTs: asynchronous 1.45 ms/commit, synchronous 7.60 ms/commit (5.2x)
With synchronous commit the primary only reports success after the standby has the WAL on disk:
RPO = 0 (no committed transaction can be lost in a failover), paid for with extra latency.

========================================================================================
C8  Failover - the primary fails, the replica is promoted
========================================================================================
docker stop -t 0 gc-pg-primary   (crash, t = 0)
replica still serves reads: appointments = 123369; writes are rejected until promotion
    pg_promote() -> t
     in_recovery |     current_wal_file     
    -------------+--------------------------
     f           | 000000020000000000000021
    (1 row)
the first 8 hex digits of the WAL file name are the timeline: promotion started timeline 2,
so WAL written by the new primary can never be confused with WAL from the old one
write accepted on the promoted node at t = 2.2 s (manual promotion; Patroni would do this automatically in ~10-30 s)
Split-brain risk: if the old primary came back as a writer, two nodes would accept different writes.
Production setups fence it (Patroni + a DCS such as etcd) and re-join it as a replica with pg_rewind.
